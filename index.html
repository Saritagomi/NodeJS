What is Node.js, Really?

Foundation
🧠
The Big Idea

Node.js is a JavaScript runtime built on Chrome's V8 engine. But the more important part is what it adds on top of V8: a library called libuv, which gives Node the ability to do I/O (reading files, making network requests) without blocking.

Before Node, JavaScript only ran in browsers. Ryan Dahl took V8 out of Chrome in 2009, wrapped it with libuv for non-blocking I/O, and created Node.js — making JavaScript a first-class server-side language.

⚙️
V8 Engine

Google's open-source JavaScript engine, written in C++. It compiles JS to native machine code using JIT (Just-In-Time) compilation. This is why modern JS is fast — it's not interpreted line by line; it's compiled.

🔄
libuv

A C library that handles asynchronous I/O, the event loop, thread pool, and OS-level abstractions. Without libuv, Node would just be V8. libuv is what makes the "non-blocking" magic real.

🧵
Single-Threaded (JS side)

Your JavaScript code always runs on one thread. But Node itself uses multiple OS threads internally — libuv has a thread pool for operations that can't be done asynchronously at the OS level.

🚀
Non-blocking I/O

When you ask Node to read a file, it registers a callback and immediately moves on. When the OS finishes reading, Node runs your callback. Your thread is never sitting idle waiting for disk or network.

ℹ Why Node is great for I/O, not CPU

Node excels at handling many concurrent I/O-bound operations — API servers, real-time apps, proxies. But for CPU-heavy work (video encoding, matrix math, image processing), one Node process is limited to one CPU core. You need Worker Threads or child processes to use multiple cores.

The Event Loop

Core
🔁
What is the Event Loop?

The event loop is the mechanism that allows Node to perform non-blocking I/O operations — despite JavaScript being single-threaded. Think of it as a continuously running loop that checks: "Is there any work to do?" If yes, it does it. If no, it waits.

Here's the mental model: Imagine a restaurant kitchen. The chef (your JS thread) takes orders (function calls), puts them on the pass (callback queue), and keeps cooking. When an order is ready (I/O completes), it comes back on the pass. The chef never stands idle waiting — they always pick up the next thing.

The 6 Phases — What Happens in Each

The event loop runs in phases. Each phase has a queue of callbacks to process. It goes through them all before moving to the next phase. This cycle repeats as long as there's work to do.

  • Phase 1: TimersRuns callbacks from setTimeout() and setInterval() whose delay has passed. The timer doesn't fire exactly at the delay — it fires when the event loop reaches this phase after the delay has passed.
  • Phase 2: Pending I/OHandles I/O callbacks that were deferred to the next loop iteration — mostly error callbacks from the previous cycle (e.g., TCP errors on some systems).
  • Phase 3: Idle/PrepareUsed only internally by Node.js. You'll never interact with this phase directly.
  • Phase 4: Poll ⭐The most important phase. Retrieves new I/O events from the OS. Executes I/O-related callbacks (e.g., file reads, network responses). If there's nothing to do, it blocks here waiting — this is where Node "waits" efficiently without burning CPU.
  • Phase 5: CheckRuns setImmediate() callbacks. This always runs after the poll phase, so setImmediate fires after I/O is processed — which is why it's often faster than setTimeout(fn, 0) inside I/O callbacks.
  • Phase 6: CloseRuns close event callbacks — e.g., socket.on('close', ...). This is where cleanup happens when connections or streams are destroyed.
⚡ The Microtask Queue — Higher Priority Than All Phases

Between every single phase of the event loop, Node drains two special queues before moving on. First it empties the nextTick queue (all process.nextTick() calls), then the microtask queue (all Promise callbacks and queueMicrotask() calls). This means microtasks can starve the event loop if you're not careful — an infinite loop of nextTick calls will block everything.

⚠ The Most Common Event Loop Mistake

Blocking the event loop with synchronous CPU work. If you run a tight loop, heavy JSON.parse, or a slow regex on the main thread — every other request waiting on your server gets frozen. There are no threads to handle them. This is why you should never call fs.readFileSync in a request handler and why JSON.stringify on a 50MB object in a request is a silent killer.

The libuv Thread Pool — Node's Hidden Threads

Some operations can't be made async at the OS level — like reading files with the POSIX API. For these, libuv maintains a thread pool of 4 workers by default. When you call fs.readFile(), Node hands it to a pool thread which does the blocking work, then passes the result back to the event loop when done. The key insight: these threads are invisible to your JS code — you still write callbacks/promises, but behind the scenes, real OS threads are doing the work.

This pool also handles dns.lookup(), heavy crypto operations, and zlib compression. If all 4 threads are busy, subsequent calls queue up — which is why a server doing many simultaneous file reads can stall. You can raise the pool size via the UV_THREADPOOL_SIZE environment variable (max 128).

Module System

Core
📦
Two Module Systems — Why They Both Exist

Node originally used CommonJS (CJS) — a module format invented for Node itself. Years later, JavaScript standardized ES Modules (ESM) in the language spec. Now Node supports both, which creates a sometimes-confusing interoperability story.

The fundamental difference: CJS modules are loaded synchronously — when you call require(), Node halts, loads the file, and returns the exports. ESM modules are analyzed statically before execution — Node can know all imports before running any code. This is what enables tree-shaking (removing unused code) in bundlers.

📦
CommonJS (CJS) — The Original

Uses require() and module.exports. Synchronous loading. Every file is executed and its exports cached on first require. Subsequent requires return the cached version — which means circular dependencies return a partial exports object (whatever was exported before the cycle was detected). Works in .js files when package.json has no "type" field.

⚡
ES Modules (ESM) — The Future

Uses import/export. Statically analyzed — Node reads all import statements before executing any code. Supports top-level await (the module itself can be async). Uses live bindings — if an exported variable changes, the importer sees the new value. Needs .mjs extension or "type": "module" in package.json.

💡 The Dual Package Pattern

When publishing a library that supports both CJS and ESM users, use the "exports" field in package.json to point to different files for each. You build your code twice (once as .cjs, once as .mjs) and let Node pick the right one automatically. This is called a "dual package" and is the current industry standard for npm libraries.

Module Caching — An Important Detail

In CJS, every module is cached by its resolved filename after the first load. Call require('./config') 10 times — the file is only read and executed once. This is usually a feature (performance), but can surprise you in tests when you want a fresh module. You can manually delete from require.cache to force a re-evaluation. ESM has no cache-busting mechanism — you'd need a cache-busting URL query string, which is awkward.

Async Patterns

Core
⏳
Three Eras of Async in Node

Node's async story has evolved through three generations. Era 1 — Callbacks (2009): Pass a function, get called when done. Works but leads to "callback hell" — deeply nested code that's hard to read and error-handle. Era 2 — Promises (2015): Return an object representing a future value. Chainable with .then() / .catch(). Better, but still verbose. Era 3 — async/await (2017): Syntactic sugar over Promises that makes async code look synchronous. This is what you should write today.

📞
Promise.all()

Runs multiple promises in parallel. Resolves when all resolve. Fails fast — if any one rejects, the whole thing rejects immediately (other promises are still running, but their results are ignored). Use when you need all results and any failure is fatal.

🧳
Promise.allSettled()

Like Promise.all() but never rejects. Waits for every promise to either resolve or reject, then gives you an array of outcome objects. Use when you want all results even if some fail — e.g., sending notifications where partial success is acceptable.

🏁
Promise.race()

Returns the result of whichever promise settles first — resolve or reject. Classic use: timeout pattern. Race your actual operation against a setTimeout promise and if the timeout wins, abort the real operation.

AbortController — Cancelling Async Operations

The web platform gave us AbortController — a standard way to cancel async operations. You create a controller, pass its .signal to any operation that supports it (fetch, file reads, timers, custom code), and call .abort() when you want to cancel. The signal propagates through the entire async chain. Node 20 added AbortSignal.timeout(ms) as a shorthand — no need to manually call setTimeout + abort().

Async Generators — Lazy Async Sequences

An async generator is a function that can pause at each yield and do async work. It produces values one at a time, on demand. This is perfect for things like API pagination (fetch page 1, yield each item, fetch page 2 only when needed) or processing a large dataset in chunks without loading it all into memory. You consume async generators with for await...of, which handles the async nature automatically.

⚠ Common Async Pitfalls

1. forEach + async: array.forEach(async item => {...}) launches all the async functions but doesn't wait for them — forEach doesn't know about Promises. Use for...of with await for sequential, or Promise.all(array.map(...)) for parallel.

2. Missing await: Calling an async function without await means you get a Promise back (not the value) and any error silently disappears into an unhandled rejection.

3. Sequential when parallel would do: Writing const a = await fetchA(); const b = await fetchB(); runs them one after another. If they're independent, use const [a, b] = await Promise.all([fetchA(), fetchB()]) — potentially 2x faster.

Streams & Backpressure

API
🌊
Why Streams Exist

Imagine you need to serve a 2GB video file. Without streams, you'd do: read entire 2GB into memory → send to client. For 100 concurrent users, that's 200GB of RAM. Not feasible. With streams, you read a chunk (say 64KB), send it, read the next chunk, send it — and your memory usage stays near zero regardless of file size or concurrent users.

Streams are Node's way of handling data that's too large to hold in memory or data that arrives over time (like a network connection). They're also composable — you can pipe a read stream through a compression transform through an encryption transform through a write stream, and it all works with proper backpressure.

📥
Readable Stream

A source of data. Can be in flowing mode (pushes data via 'data' events as fast as it can) or paused mode (you call read() to pull chunks when ready). File reads, HTTP request bodies, database query results — all readable streams.

📤
Writable Stream

A destination for data. You call write(chunk) to push data in. The stream has an internal buffer — when it's full, write() returns false to signal "slow down." HTTP response objects, file write streams — all writables.

🔀
Transform Stream

Both readable and writable — data goes in one side, modified data comes out the other. zlib compression, encryption, CSV parsing, JSON serialization — all transforms. You implement _transform(chunk, enc, callback) to define the modification.

🔌
Duplex Stream

Also both readable and writable, but the two sides are independent — output is not derived from input. TCP sockets are duplex: you send data on the write side and receive data on the read side, but one doesn't influence the other.

Backpressure — The Most Misunderstood Part

Backpressure is the mechanism that prevents a fast producer from overwhelming a slow consumer. Imagine a fast file read streaming into a slow network write: if you ignore backpressure, the unwritten chunks pile up in memory — you've just defeated the whole point of streams.

When a writable's internal buffer is full, write() returns false. At that point, you must stop writing and wait for the 'drain' event, which fires when the buffer has been flushed and is ready for more. The pipeline() function handles all of this for you automatically — it also properly destroys all streams in the chain if any one of them errors, which .pipe() does not do.

🔴 Always use pipeline(), not .pipe()

stream.pipe(dest) handles backpressure but does NOT propagate errors — if the source errors, the destination is not destroyed and you leak resources. pipeline(src, ...transforms, dest) from stream/promises handles backpressure AND destroys all streams on error AND returns a Promise. Always use it.

import { pipeline } from 'stream/promises';
import { createReadStream, createWriteStream } from 'fs';
import { createGzip } from 'zlib';

// Read → compress → write. Backpressure and errors handled automatically.
await pipeline(
  createReadStream('big-file.csv'),
  createGzip(),
  createWriteStream('big-file.csv.gz')
);

Buffers & Binary Data

API
🧱
Why Buffers Exist

JavaScript strings are Unicode (UTF-16 internally). But when you're dealing with files, network packets, images, or cryptographic data — you're working with raw bytes, not characters. Buffer is Node's way to represent a sequence of raw bytes.

Crucially, Buffer memory is allocated outside V8's heap. This means it doesn't count toward your JavaScript heap limit, isn't managed by V8's garbage collector in the normal way, and can be passed to OS-level operations without copying. A Buffer is a subclass of Uint8Array — so all typed array methods work on it too.

✅
Buffer.alloc(size)

Creates a buffer of size bytes, all initialized to zero. Slightly slower but safe — no risk of exposing old memory contents. Always use this for buffers that will be sent to users or clients.

⚡
Buffer.allocUnsafe(size)

Creates a buffer of size bytes, NOT zeroed out. Faster, but the buffer may contain sensitive data from previous memory allocations. Only use when you'll immediately fill the entire buffer before using it.

🔴 Security: allocUnsafe is a data leak risk

Buffer.allocUnsafe() recycles memory that previously held other data — this could be old passwords, tokens, or private keys from earlier in your process lifetime. Never send an allocUnsafe buffer to a client without fully writing to every byte first.

Encodings — Reading Bytes as Different Formats

A buffer is just bytes. The same bytes can be interpreted as UTF-8 text, as hex, as base64, or as raw binary integers. When you call buf.toString('hex'), you're not changing the buffer — you're just reading those bytes as hexadecimal characters. This is fundamental to understanding how Node handles things like HMAC signatures (raw bytes interpreted as hex) or JWT tokens (JSON bytes interpreted as base64url).

File System

API
📁
Three Styles, One Rule

Node's fs module exposes three flavors: callback-based (fs.readFile(path, cb)), promise-based (import from 'fs/promises'), and synchronous (fs.readFileSync(path)). The rule is simple: always use fs/promises in any code that handles requests or runs frequently. Sync methods block the entire event loop while reading — meaning every concurrent user is frozen waiting for your disk operation to complete.

The only acceptable use of sync methods is during application startup — reading a config file once before the server starts listening is fine because no users are connected yet.

  • Atomic WritesWhen updating a file (like a config or data file), never write directly to the target file. If your process crashes mid-write, you're left with a corrupt file. Instead: write to a temp file (e.g., config.json.tmp), then call rename(). A rename on the same filesystem is atomic at the OS level — it either completes or doesn't. No corrupt state.
  • Existence ChecksDon't use existsSync() followed by an action — there's a race condition (another process could delete the file between your check and your action). Instead, just try to open/read the file and handle the ENOENT error code. This is the TOCTOU (Time-Of-Check-Time-Of-Use) problem.
  • File Watchingfs.watch() uses OS-level file system events (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows). It's efficient but has OS-specific quirks — macOS might fire two events for one change, Linux might miss events on NFS. Node 22 stabilized recursive directory watching.
  • Walking DirectoriesUse opendir() + for await...of instead of readdir(). It reads directory entries lazily as you iterate, rather than loading all filenames into an array first. For a directory with 100,000 files, this is a significant memory difference.
💡 Large file reading

If you're reading files larger than ~10MB, use streams (createReadStream) instead of readFile(). readFile() loads the entire file into a Buffer in memory. For a 1GB log file, that's 1GB of RAM gone for that one request — and if 10 users do it simultaneously, you've OOM-crashed your server.

HTTP & Networking

Performance
🌐
HTTP/1.1, HTTP/2 — What's the Difference?

HTTP/1.1 opens one TCP connection per request (or uses keep-alive to reuse connections, but still processes requests serially). If you make 6 simultaneous requests to a server, your browser opens 6 connections. This is inefficient — TCP handshakes, SSL negotiation, and head-of-line blocking where a slow first request delays everything behind it.

HTTP/2 uses a single TCP connection with multiplexing — all requests share one connection, sent as independent "streams" interleaved at the frame level. A slow request doesn't block fast ones. Header compression (HPACK) reduces overhead significantly. Node's built-in http2 module supports all of this without external libraries.

Native fetch — Node 18+

Node 18 added the browser-standard fetch() API as a global — no import needed. It returns a Promise and works exactly like browser fetch. Node 20 added AbortSignal.timeout(ms) for ergonomic timeouts. For most use cases, native fetch replaces axios, node-fetch, and got. The main thing it still lacks vs those libraries: automatic retry logic and request interceptors.

♻️
Keep-Alive Agents

By default, Node creates a new TCP connection for each HTTP request. Keep-alive agents reuse TCP connections across requests to the same host — eliminating the connection setup overhead (TCP handshake: ~1ms, TLS handshake: ~5–30ms). For a service making 1000 requests/second to an external API, this is enormous.

🧩
dns.lookup vs dns.resolve

dns.lookup() uses the OS resolver — it reads /etc/hosts, respects system DNS config, and runs in the libuv thread pool. dns.resolve4() goes directly to a DNS server asynchronously. In Kubernetes/Docker, always prefer dns.resolve*() for predictable latency and to avoid thread pool saturation.

ℹ TCP socket options you should know

socket.setNoDelay(true) — Disables Nagle's algorithm. By default, TCP buffers small packets to send together (Nagle). Disabling it reduces latency at the cost of slightly higher bandwidth. Essential for real-time protocols like SSH, gaming, or financial data where every millisecond counts.

socket.setKeepAlive(true, 60000) — Sends TCP keep-alive probes every 60 seconds. This detects dead connections (where the remote side disappeared without a clean close) and lets you recover resources. Without it, you can accumulate zombie connections indefinitely.

EventEmitter

Core
📡
Node's Observer Pattern

EventEmitter is Node's built-in implementation of the observer/pub-sub pattern. An object emits named events, and any number of listeners subscribe to those events. Nearly everything in Node's core extends EventEmitter — streams, HTTP servers, child processes, the process object itself.

When you call emitter.emit('data', chunk), all listeners registered for 'data' are called synchronously in registration order, in the current tick. This is different from how browser DOM events work — there's no async dispatch, no bubbling, no capturing. Just synchronous calls.

  • .on(event, fn)Registers a persistent listener. Stays registered until you explicitly remove it with .off() or .removeListener(). The most common source of memory leaks in Node apps — you add a listener in a loop and never clean it up.
  • .once(event, fn)Registers a listener that automatically removes itself after firing once. Perfect for "wait for this thing to happen one time" — database connection ready, server started, first user authenticated.
  • .off(event, fn)Removes a specific listener. The function reference must match exactly — you can't remove an anonymous function added with an inline arrow function. Always keep a reference to handlers you'll need to remove.
  • Max listener warningBy default, Node warns when more than 10 listeners are added to a single event — this is often a sign of a memory leak (adding listeners in a loop). You can raise the limit with setMaxListeners(), but first check if you're actually leaking.
  • 'error' eventCritical: If an 'error' event is emitted and there's no listener for it, Node throws the error and potentially crashes the process. Always add an error handler to every EventEmitter you use.
  • captureRejectionsNode 12+ option. If an async listener throws a rejected Promise, normally it creates an unhandled rejection. With captureRejections: true, the rejection is captured and emitted as an 'error' event instead — much cleaner.
💡 Converting events to Promises

Use events.once(emitter, 'eventName') to get a Promise that resolves the next time the event fires. This lets you use await with event-based APIs: await once(server, 'listening'). For streaming all occurrences of an event as an async iterable, use events.on(emitter, 'eventName') with for await...of.

Child Processes

System
👶
When You Need Another Process

Sometimes you need to run another program — a CLI tool, a Python script, a compiled binary. Or you need to run CPU-heavy Node.js code without blocking your main event loop. Child processes let you spawn OS-level processes, communicate with them, and react when they finish.

The key distinction between the four APIs is whether you want buffered output (wait for it all, then get a string) vs streamed output (receive chunks as they arrive), and whether you need a shell (to use shell features like pipes, globs, environment expansion) or just a binary.

FunctionOutput styleSpawns a shell?Best for
exec()Buffered (string)Yes ⚠️Short commands where you need the full output as a string. Shell injection risk with user input.
execFile()Buffered (string)No ✅Same as exec but safer — runs the binary directly. Use when you control the command args.
spawn()StreamingNo ✅Long-running processes (ffmpeg, npm install). Streams stdout/stderr. No memory limit on output.
fork()Streaming + IPCNo ✅Node.js child processes that need to communicate back. Each fork is a full Node process.
🔴 Shell injection with exec()

Never construct a shell command by interpolating user-supplied data: exec(`convert ${userFile} output.png`). If userFile is ; rm -rf /, you've just deleted everything. Always use execFile() or spawn() with an args array — the arguments are passed directly to the OS without shell interpretation.

fork() and IPC — Communicating With a Child

When you fork a Node.js child process with fork(), Node sets up an IPC (Inter-Process Communication) channel automatically — a pipe between the parent and child. You can pass JavaScript objects back and forth with process.send() / child.send() and receive them with the 'message' event. The objects are serialized to JSON (or structured clone). This is great for offloading computation to a child process while maintaining a clean API.

Worker Threads

Performance
🧵
Workers vs Child Processes — When to Use Which

Both Workers and fork() let you run code in parallel, but they're fundamentally different. A child process is a completely separate OS process — its own memory space, its own V8 instance, its own event loop. They're isolated: a crash in one doesn't affect others. Communication is via IPC (slower serialization).

A Worker Thread runs inside the same OS process, with its own V8 context and event loop, but shares the same memory space (specifically, SharedArrayBuffer). Workers start in ~2–5ms vs ~50–100ms for a full process fork. Communication via postMessage uses structured clone (serialization) by default, but you can use zero-copy transfers of ArrayBuffer ownership for performance-critical data.

📨
MessageChannel & postMessage

Workers communicate via message passing. Each postMessage() call deep-clones the data by default — like JSON.stringify but supporting more types. For large data (say, a 10MB TypedArray), this copy is expensive. Instead, transfer ownership of the buffer — after transfer, the sender can no longer access it, but no copy is made.

🔒
SharedArrayBuffer & Atomics

SharedArrayBuffer lets multiple threads read and write the same memory simultaneously. Atomics provides lock-free operations on that shared memory — guaranteed atomic read-modify-write operations, and Atomics.wait()/notify() for blocking synchronization. This is low-level concurrency — use only when message passing is too slow.

💡 The Worker Pool Pattern

Never create a new Worker for each incoming request — Worker startup costs ~5ms and each worker uses significant memory. Instead, create a fixed pool of workers at startup (typically N = CPU core count) and reuse them. When a task comes in, assign it to an idle worker. When the worker finishes, it returns to the pool. The piscina library implements this efficiently and is the de-facto standard for Node worker pools.

Cluster Mode

Performance
🔢
Making Node Use All CPU Cores

A single Node process can only use one CPU core. If your server has 16 cores, you're leaving 15 cores idle. Cluster mode solves this by spawning multiple Node processes (workers) that all share the same server port. The OS distributes incoming connections among them using round-robin (Linux/macOS) or its own scheduling (Windows).

Each cluster worker is a completely independent process — own heap, own event loop, own module cache. If one worker crashes, the others keep running. The primary process (the one that calls cluster.fork()) doesn't handle requests itself — it only manages the workers.

🔃
Zero-Downtime Restarts

When you deploy new code, you don't want to kill all workers simultaneously (that causes downtime). Instead, kill one worker at a time — wait for the primary to spawn a replacement and confirm it's listening before killing the next. This is called a rolling restart and keeps your service running throughout a deployment.

🔁
Auto-Restart on Crash

Listen to the 'exit' event on the cluster module. When a worker exits, call cluster.fork() again. This makes your application self-healing — individual worker crashes are automatically recovered without manual intervention. Always log the exit reason so you know when workers are crashing.

ℹ Cluster vs Container Orchestration

Cluster is great when running Node on a bare VM or single server. In Kubernetes or Docker Swarm, the orchestrator handles replication — you run a single-process Node container and let K8s scale replicas. Cluster adds unnecessary complexity in that world. PM2 is a middle ground: it wraps cluster with process management, auto-restart, and log management — useful on single servers without orchestrators.

Error Handling

Production
🚨
Operational vs Programming Errors

There are two categories of errors in Node. Operational errors are expected, runtime failures: database is down, user sent invalid input, network timeout, disk is full. You should handle these gracefully — log them, return an appropriate HTTP error, maybe retry. Programming errors are bugs: calling a function with the wrong type, accessing a property on null, undefined is not a function. These indicate a bug in your code and often the correct response is to crash and restart so you're not running corrupted state.

  • Custom Error ClassesExtend Error to add context. Add a code property (e.g., 'ERR_NOT_FOUND') so you can programmatically distinguish error types. Add a statusCode for HTTP errors. Use Error.captureStackTrace(this, this.constructor) to ensure the stack trace points to where the error was created, not inside your error class constructor.
  • Error.cause (ES2022)Chain errors without losing context: new Error('Failed to save user', { cause: dbError }). The original error is preserved in err.cause. Essential for debugging — you see the full chain: "Failed to save user" caused by "Connection timeout" caused by "ETIMEDOUT".
  • uncaughtExceptionFires when a thrown error is never caught anywhere in the call stack. You must exit the process after handling it — the application is in an undefined state. Log the error, flush logs, exit with code 1. Never try to resume normal operation after an uncaughtException.
  • unhandledRejectionFires when a Promise rejects and no .catch() or try/catch handles it. In Node 15+, this automatically exits the process (code 1). Log it before exit. The root cause is almost always a missing await or a floating Promise chain.
  • Graceful ShutdownOn SIGTERM (Docker stop, K8s pod eviction) or SIGINT (Ctrl+C): stop accepting new connections, finish in-flight requests (with a timeout), close DB connections, flush logs, then exit. The timeout ensures you don't hang forever if some requests are stuck.
🔴 Never swallow errors silently

catch(() => {}) is one of the most dangerous patterns in Node. The error is gone — no logs, no metrics, no way to know something went wrong. Future symptoms will be mysterious and hard to diagnose. At minimum, log every error you catch. If you genuinely can ignore an error, add a comment explaining exactly why.

Crypto & Security Patterns

API
🔐
Node's Built-in Crypto Module

Node ships with a comprehensive crypto module built on OpenSSL. You rarely need third-party crypto libraries for common operations — hashing, HMAC, encryption, key generation, signing, and random number generation are all covered. Node 19+ also exposes the Web Crypto API (globalThis.crypto.subtle) which matches the browser API exactly, useful for code that runs in both environments.

🎲
Secure Randomness

Always use crypto.randomBytes() for security-sensitive random data — session tokens, CSRF tokens, password reset links. Never use Math.random() for anything security-related — it's deterministic and not cryptographically secure. crypto.randomUUID() generates a compliant v4 UUID. crypto.randomInt(min, max) gives a secure random integer (useful for OTPs).

🕐
Timing-Safe Comparison

When comparing two secrets (HMAC signatures, tokens, passwords), never use ===. Normal string comparison short-circuits as soon as it finds a mismatch — an attacker can measure how long the comparison takes and deduce the secret byte by byte (timing attack). Use crypto.timingSafeEqual() which always takes the same time regardless of where the mismatch is.

🔑
Password Hashing — Use scrypt

Passwords must be hashed with a slow, memory-hard algorithm designed to resist brute-force attacks. Node's built-in crypto.scrypt() is the best choice — it's memory-hard (hard to parallelize on GPUs), tunable, and doesn't require any npm packages. bcrypt is also acceptable but requires a native module. Never use SHA256 or MD5 for passwords — they're too fast (a GPU can try billions/sec).

🔒
Symmetric Encryption — AES-256-GCM

For encrypting data at rest or in transit, use AES-256-GCM. GCM mode provides authenticated encryption — it both encrypts the data AND generates an authentication tag that detects tampering. Without authentication, an attacker can modify encrypted data without you knowing. Never use AES-CBC without a separate MAC — use GCM instead.

⚠ HMAC for webhook verification

When your service receives webhooks (Stripe, GitHub, etc.), always verify the signature. The sender computes an HMAC-SHA256 of the request body using your shared secret and sends it as a header. You compute the same HMAC and compare with timingSafeEqual(). Without this check, anyone can send you fake webhook events.

Performance & Diagnostics

Performance
📊
How to Actually Find Performance Problems

Performance debugging in Node has two main categories: event loop lag (JavaScript is too slow — something blocks the loop) and I/O bottlenecks (code is waiting too long for external systems). They have very different root causes and tools.

Event loop lag means your JavaScript is running synchronous code for too long between yielding. Symptom: high response time variability — some requests are fast, some are randomly slow. Flamegraph profiling reveals this. I/O bottlenecks mean you're waiting on DB, disk, or network. Symptom: consistent slowness. Clinic.js's bubbleprof visualization reveals this.

  • --inspect flagStart Node with --inspect and open Chrome's DevTools. You get a full debugger: breakpoints, call stack, memory profiler, CPU profiler, and heap snapshots — all in the browser. --inspect-brk additionally pauses execution on the first line, useful for debugging startup issues.
  • CPU Profilingnode --prof server.js generates a V8 tick log. Run node --prof-process isolate-*.log to convert it to a human-readable flamegraph summary. The flamegraph shows which functions consume the most CPU — your optimization targets are at the widest parts of the flame.
  • Heap SnapshotsTake a heap snapshot before and after a suspected memory leak using v8.writeHeapSnapshot() or Chrome DevTools. Load both into Chrome's Memory tab and use "Comparison" view to see what objects were created and not garbage collected between the two snapshots.
  • AsyncLocalStorageAllows you to attach contextual data (request ID, user ID, trace ID) to the current async execution context — and read it from anywhere in the async call chain without passing it as a parameter. Essential for structured logging in production. This is how frameworks like Fastify and Next.js attach request context.
  • Event Loop LagMeasure how much the event loop falls behind by scheduling a callback every 1 second and measuring how late it actually fires. If you scheduled for 1000ms and it fires at 1150ms, you have 150ms of event loop lag — something ran synchronously for too long. This is a critical production metric.
  • perf_hooksThe built-in perf_hooks module provides high-resolution timing (performance.now() with nanosecond precision), performance marks, measures, and a PerformanceObserver for monitoring HTTP requests, GC events, and custom marks programmatically.

V8 & Memory Management

Performance
🧠
How V8 Manages Memory

V8 uses a generational garbage collector based on a key observation: most objects die young. Objects that are created and immediately discarded should be collected cheaply and often. Objects that survive many GC cycles are likely long-lived and should be collected rarely but thoroughly.

This leads to two "generations": the Young Generation (small, collected frequently with a fast algorithm called Scavenge) and the Old Generation (large, collected infrequently with a slower Mark-Sweep algorithm). Understanding this helps you write code that creates less GC pressure.

🌱
Young Generation (Nursery)

New objects start here. Only 1–8MB in size. V8 uses a Scavenge algorithm — it copies surviving objects to a second space, leaving the original space empty (no fragmentation). Collection takes ~1ms. Objects that survive two collections get promoted to Old Generation.

🌳
Old Generation

Long-lived objects live here. Default max heap ~1.4GB on 64-bit. V8 uses Mark-Sweep-Compact — marks all reachable objects, sweeps unreachable ones, then compacts to eliminate fragmentation. This can take 10–100ms+ and pauses the event loop. Increase with --max-old-space-size=4096 (MB).

Common Memory Leak Patterns — Know These Cold
  • Event listeners not removed: Adding a listener in a request handler but never calling .off(). Each request adds another listener until you have thousands.
  • Closures holding large scope: An async callback captures a large variable in its closure. If that callback is stored somewhere (like a queue or timer), the large object can't be GC'd.
  • Unbounded caches: A Map or object used as a cache that grows forever. Always set a maximum size or TTL. Use lru-cache for proper LRU eviction.
  • setInterval with growing data: An interval that accumulates data in a closure-captured array without ever clearing it.
  • Global arrays/maps: Appending to a module-level array inside a request handler — the array grows with every request and is never cleaned up.
✦ WeakRef and FinalizationRegistry

WeakRef (Node 14+) lets you hold a reference to an object without preventing it from being garbage collected. If the object gets GC'd, weakRef.deref() returns undefined. FinalizationRegistry lets you register a cleanup callback to run when an object is GC'd. Together these enable GC-aware caches where entries automatically clean up when their associated objects die — without memory leaks.

Node 20–23: What's New & Why It Matters

New
🚀
Node is Catching Up Fast

The last four Node versions (20–23) have dramatically reduced the need for external packages. Things that used to require dotenv, jest, node-fetch, ws, better-sqlite3, and ts-node are now built-in. Here's what changed and why it matters for your stack.

  • Native Test Runner
    (Node 18+)    import { test, describe, mock } from 'node:test' — a full test runner built into Node. Supports async tests, subtests, mocking, code coverage (--experimental-test-coverage), and TAP/spec reporters. For most projects, this eliminates the need for Jest or Mocha. Run with node --test.
  • Native fetch
    (Node 18, stable 21)    The browser-standard fetch() API is now a global — no import, no node-fetch, no axios for simple cases. Includes Request, Response, Headers, FormData, ReadableStream. Node 20 added AbortSignal.timeout() shorthand.
  • Native WebSocket
    (Node 22)    The WebSocket global (client-side) is now stable in Node 22. No more ws package for WebSocket clients. Note: this is the client WebSocket API — for WebSocket servers you still need a library like ws.
  • .env file loading
    (Node 20.6+)    Start your app with node --env-file=.env server.js and Node reads the .env file and sets process.env before running your code. Multiple --env-file flags are supported. No more require('dotenv').config() at the top of every entry point.
  • Built-in SQLite
    (Node 22.5+)    import { DatabaseSync } from 'node:sqlite' — a synchronous SQLite interface built directly into Node. Zero native compilation, zero npm packages. Perfect for CLIs, embedded data, caching, and small apps. Uses better-sqlite3's API style (synchronous, which is fine since SQLite reads are fast).
  • import.meta.dirname
    (Node 21.2+)    Finally — ESM modules now have import.meta.dirname and import.meta.filename. No more awkward fileURLToPath(import.meta.url) dance to get the current file's directory. Works exactly like __dirname in CommonJS.
  • TypeScript support
    (Node 22.6+)    node --experimental-strip-types server.ts — Node strips TypeScript type annotations and runs the file directly. No build step, no ts-node, no tsx. Limitation: only type stripping, no enum or decorator transformation (use --experimental-transform-types for those in Node 22.7+).
  • Compile Cache
    (Node 22.8+)    node --compile-cache=./cache server.js — Node saves compiled V8 bytecode to disk and reuses it on subsequent starts. This can reduce cold-start time by 30–60%, especially for large applications with many modules. The cache is automatically invalidated when files change.
  • require(ESM) unflagged
    (Node 23)    You can now require() synchronous ES modules from CommonJS code without any flags. This was a long-awaited bridge between the two module systems — you no longer need to refactor your entire codebase to ESM just to use a library that ships ESM-only.
  • os.availableParallelism()
    (Node 19+)    Better than os.cpus().length for determining how many workers to spawn. Respects cgroup CPU quotas (Docker container CPU limits) and returns the number of CPUs actually available to the process, not the total on the host machine.
✦ The Trend: Less npm, More Node

Node's core team is deliberately reducing the ecosystem's dependency on third-party packages for foundational tooling. The goal: a project should be able to test, run TypeScript, make HTTP requests, use SQLite, watch files, and load environment config — all with zero npm installs. This improves security (fewer supply-chain attack surfaces), startup time, and reduces project complexity.
